# SIDA Phase 10–14 Implementation Plan

> **For Hermes:** use `subagent-driven-development`. One subagent per feature
> track (A–F below). Each track owns a disjoint set of files — see §2 — so
> they can run in parallel without merge conflicts.

**Goal:** close the gaps that make the platform unusable in daily school
operation, before starting anything large (LMS, site builder).

**Architecture:** six independent feature tracks. Five of the six add only
screens on top of tables that already exist. Nothing here needs a new
migration except track D, which needs one table.

**Tech Stack:** Laravel 12, Blade + Alpine (the existing `x-card`,
`x-form-field`, `x-status-badge`, `x-alert` components), Spatie permission,
MySQL 8.4. Tests: PHPUnit via `docker compose exec -T app php artisan test`.

---

## 0. The facts this plan is built on

Verified against the code, not the docs — `docs/MODULE_MAP.md` had drifted
and was corrected in `b64989e`.

**Grading data already exists and is complete.** `grades` is keyed
`(enrollment_id, subject_id, term)` with `score decimal(5,2)`,
`status draft|published`, `teacher_id`, `published_by`, `published_at`.
`semesters` + `grade_categories` exist from Phase 1, and `semester_id` was
added to `grades` as a **nullable** column with an idempotent backfill. So
grade entry needs **no migration**.

**Announcements exist but cannot be edited.**
`AnnouncementController` has `index`, `create`, `store`, `destroy` and no
`update`. `classroom_announcements` has every column needed. No migration.

**Guardian linking has no UI at all.** `guardian_relationships` exists
(`2026_09_27_050100`), `ParentGuardian` model exists, and
`guardian.view` / `guardian.link` / `guardian.unlink` are granted to real
roles and reach nothing.

**Media is the one track that needs a new table.** There is no `cms_media`
table, no model, no upload. `cms.media.manage` cannot be implemented without
it.

**Dead permissions — 23 of them** are in `PermissionCatalog` and are granted
to roles that display them in the role matrix while no code consults them.
Seven tracks below either implement or remove these.

## 1. Ordering and why

```
Track A  gradebook          ─┐
Track B  announcements      ─┤  independent, run together
Track C  guardian links     ─┘
Track D  CMS media          ─┐
Track E  workflow wiring    ─┤  independent
Track F  operator surfaces ─┘  (module toggle, employee self-service)
```

A, B, C are "core school operation" — a school cannot run a term without them.
D is "site work". E is "fix a build that exists but is unused". F is "stop
requiring the CLI".

**None of them touch each other's files.** §2.

## 3. Track A — Grade entry

**The problem:** `grades` is populated by nothing. A parent portal reads
grades; a report aggregates them. No human can enter one. `grade.edit` and
`grade.publish` are dead permissions.

**The design decision that must not be got wrong:** entry and publication are
separate permissions, because a teacher marking a test is not a head
publishing a report card. `grades.status` stays `draft` on save; only
`grade.publish` moves it to `published` and stamps `published_by` /
`published_at`. A parent must never see a draft.

### Task A1: service and policy

Create `app/Services/GradeEntryService.php`:

- `roster(SchoolClass $classroom, ?Semester $semester): Collection` — active
  enrollments joined to `subjects`, one row per student
- `save(SchoolClass, Semester, Subject, array $scores, User $teacher)` — one
  `updateOrCreate` per non-empty score, keyed on the DB's own
  `(enrollment_id, subject_id, term)`; **skip** rather than null a row the
  teacher cleared, so a cleared cell is not a deletion (the unique constraint
  plus a nullable score makes "deleted" ambiguous)
- `publish(SchoolClass, Semester, array $subjectIds, User $actor): int`
- `classroomIdsFor(User $user): array` — **reuse `App\Services\ClassScope`,
  do not re-implement it.** A Wali Kelas holding `grade.edit` still must not
  open another teacher's class.

Create `app/Policies/GradePolicy.php` with `viewAny`, `view`, `edit`,
`publish`. `publish` requires `grade.publish` AND the same scope check as
`edit` — scope does not widen because someone can publish.

### Task A2: controller and routes the controller expects

`app/Http/Controllers/GradeEntryController.php` — `index`, `store`, `publish`.
Report needed routes (do not add them):
`GET /akademik/kelas/{classroom}/nilai`, `POST /akademik/kelas/{classroom}/nilai`,
`POST /akademik/kelas/{classroom}/nilai/terbitkan`.

### Task A3: views

`resources/views/academic/gradebook/index.blade.php` — one row per student,
one column per subject, `x-form-field` for each cell, a publish button that
only renders under `@can('grade.publish')`. A blank cell must submit as blank
and mean "not graded", not "zero".

### Task A4: tests

`tests/Feature/GradeEntryTest.php` — at minimum:

- a teacher with `grade.edit` can save, and the row is `draft`
- saving a score does **not** make it visible to the parent portal
- publishing makes it visible
- a Wali Kelas cannot open a class they do not homeroom
- a second save updates rather than duplicates (the unique constraint)
- a cleared cell does not delete the row

Run: `docker compose exec -T app php artisan test --filter=GradeEntryTest`

## 4. Track B — Announcement edit

**The problem:** `AnnouncementController` has no `update`. A typo means
delete and recreate, and the parents who already received it got the wrong one.

### Task B1: the missing methods

Add `edit(Request, SchoolClass, ClassroomAnnouncement)` and
`update(Request, SchoolClass, ClassroomAnnouncement)` to the existing
controller, and the two routes in the report.

- `$this->authorize('update', $announcement)` — but the real check is
  **ClassScope**: the announcement must belong to a classroom the actor can
  reach, and the existing `destroy` already does this. Reuse that check
  rather than inventing a second one.
- Validate `title` 150, `body` required, `audience` in `students|parents|both`,
  `expires_at` nullable date after `published_at`.
- **Editing a published announcement must not reset `published_at`.** The
  parents already received this one; re-stamping the date is a lie.
- Audit: `announcement.updated`.

### Task B2: views and tests

`resources/views/academic/announcements/edit.blade.php` — reuse the create
form's field names exactly, so old input and validation errors behave.

`tests/Feature/AnnouncementEditTest.php`:

- an authorised teacher can edit their own classroom's announcement
- a teacher from another class gets 403 (this is the scope test)
- editing does not change `published_at`
- `audience` is validated against the three allowed values

## 5. Track C — Guardian linking

**The problem:** `guardian_relationships` exists, `ParentGuardian` exists, the
parent portal works — and there is no way to link an account to a child. The
portal is unreachable for every new student.

### Task C1: service and policy

`app/Services/GuardianService.php`:

- `link(Student, User, string $relation, bool $isPrimary): GuardianRelationship`
  — guard against a duplicate link for the same (student, user, relation)
- `unlink(GuardianRelationship)` — refuses when the child would be left with
  **no** guardian at all; a school must not be able to orphan a student's
  access silently
- `childrenFor(User $id): array` — read, for the portal's `404` behaviour

`app/Policies/GuardianPolicy.php`: `view`, `link`, `unlink` →
`guardian.view` / `guardian.link` / `guardian.unlink`.

### Task C2: controller, views, tests

`app/Http/Controllers/GuardianController.php` under `/kesiswaan/`:

- `index(Student $student)` — list the child's guardians and the staff
  accounts that are not yet linked
- `store(Student)` — link
- `destroy(Student, GuardianRelationship)` — unlink

Views in `resources/views/kesiswaan/guardians/`.

`tests/Feature/GuardianLinkTest.php`:

- an admin can link a parent account to a student
- linking the same account twice for the same relation is refused
- unlinking the last guardian is refused
- a parent who is linked sees their child; one who is not gets **404, not
  403** — a 403 confirms the record exists

## 6. Track D — CMS media

**The one track with a new table.** Additive migration, no `down()` that
touches data beyond its own table.

### Task D1: migration and model

`database/migrations/2026_10_01_000000_create_cms_media_tables.php`:

- `cms_media`: `id`, `disk` (default `public`), `path`, `original_name`,
  `mime_type`, `size_bytes`, `width`/`height` nullable, `alt_text` nullable,
  `uploaded_by` FK nullable, timestamps, softDeletes
- index on `(disk, path)`, index on `mime_type`

**Never store a user-supplied filename as the path.** Sanitise to a
random hex name plus the extension, derived from the *validated* mime type —
a path built from `$_FILES['name']` is how `../../` and a double extension
get in.

`app/Models/CmsMedia.php` — `HasFactory`, `SoftDeletes`, casts, an
`isImage()` helper, and a `url()` that goes through the app (not a raw disk
path) so a private disk is not exposed.

### Task D2: service with the validation that matters

`app/Services/CmsMediaService.php`:

- allow-list of mime types (**never** trust `getMimeType()` alone — it reads
  the file's contents, and an allow-list is the check that survives a
  mis-detected type)
- max size from the mime's own limit
- generate the stored name server-side
- delete removes the file **and** the row, in that order, so a failed row
  delete leaves a recoverable orphan rather than a row pointing at nothing

### Task D3: controller, policy, views, tests

`app/Http/Controllers/CmsMediaController.php` — `index`, `store`, `destroy`,
`show`. `app/Policies/CmsMediaPolicy.php` → `cms.media.manage`.

Views in `resources/views/admin/cms/media/` — a grid with a picker, alt-text
required for images (an image with no alt is invisible to a screen reader and
is exactly what the a11y requirement is about).

`tests/Feature/CmsMediaTest.php`:

- a valid image uploads and is retrievable
- a **disguised** executable (`.png` extension, PHP content) is refused
- an oversized file is refused
- `../` in the original filename cannot escape the disk
- an editor without `cms.media.manage` gets 403

## 7. Track E — Wire the workflow engine to PPDB verification

**The problem:** `workflow_definitions/steps/instances/actions` exist,
`WorkflowService` exists, `WorkflowEngineTest` has 12 passing tests — and
`VerificationService` still hand-rolls approve/reject. The engine is a
finished building nobody uses. This is the **highest-risk** track: it
touches a flow that works today.

### Task E1: the adapter, not a rewrite

Do **not** rewrite `VerificationService`. It works and is tested. Add a
translation layer:

- a `workflow_definitions` row seeded for `registration.verification` with
  steps bound to `verification.approve` and
  `verification.request_revision` (the engine already supports a
  permission-bound step — `WorkflowEngineTest` pins it)
- `VerificationService::approveDocument()` / `rejectDocument()` open or
  advance an instance **in addition to** what they already do
- every existing assertion in the current suites must still pass unchanged —
  that is the acceptance criterion, not a nice-to-have

### Task E2: the safety test

`tests/Feature/VerificationWorkflowTest.php` must prove the regression the
audit flagged: a **rejection reason is still recorded** in the trail, and a
**completed workflow accepts nothing further**. Those two behaviours are the
reason the flow is not simply deleted, and losing either in a refactor is the
failure this track exists to prevent.

## 8. Track F — Operator surfaces

### Task F1: module toggle screen

An operator currently has to run `php artisan sida:enable-modules` to turn a
module on. That is a CLI as a product feature.

`app/Http/Controllers/ModuleController.php` + `resources/views/admin/modules/`
— list every registry row with its state, its required flag, and a toggle.
`setEnabled()` already refuses to disable a required module and throws; catch
it and show the reason rather than a 500.

Needs permission `system.update` (currently dead) — report it, do not add it.

### Task F2: employee self-service

A staff member cannot see their own employment record. Add
`resources/views/profile/employment.blade.php` and a `ProfileController`
method — read-only, the account's own record only, 404 for anyone else's.

The trap: a person can be staff with **no** employment record (Phase 3
deliberately did not backfill). The view must say so rather than error.

## 9. Orchestrator duties after the tracks report

1. Apply every requested route into `routes/web.php` in one patch
2. Apply every requested nav item into `NavigationService::staffItems()`
3. Apply every permission change into `PermissionCatalog` — and **remove the
   permissions that stay dead** rather than leaving them in the role matrix
4. Register every new policy in `AppServiceProvider::boot()`
5. Add any new status to `components/status-badge.blade.php`
6. `php artisan view:clear`
7. Full suite, then commit, push to `feat/sida-platform`, then `main`
8. After deploy: `bash hermes-wasmer-migrate.sh` (track D adds a migration)
9. Verify: `curl` every public route for 200 and every admin route for 302

**Dead permissions after these tracks:** A clears `grade.edit`,
`grade.publish`. B clears `announcement.update`. C clears `guardian.*`. D
clears `cms.media.manage`. F clears `system.view`.

**Still dead, and out of scope here** — say so rather than leave them
looking implemented: `student.delete`, `student.export`, `homeroom.change`,
`classroom.announcement.update`, `alumni.view`, `registration.delete`,
`cms.pages.*`, `cms.navigation.manage`, `cms.themes.manage`,
`cms.settings.manage`, `role.assign.super_admin`, `master.update`,
`master.delete`, `dashboard.student.view`. Either implement or **delete from
the catalogue** — a permission displayed in the role matrix that no code
consults is a claim the product cannot keep.

## 10. Risks

| Risk | Mitigation |
|---|---|
| Six agents, one repo, concurrent edits | §2 exclusive ownership; shared files are orchestrator-only |
| Track E regresses a working flow | acceptance is "every current test still passes", plus the two pinned behaviours |
| Parallel `php artisan test` deadlocks | Run the full suite **once**, after all tracks. Never two test processes against the same DB — that is what produced a 1213 deadlock earlier. |
| Track D's migration hits production | additive, one table, no data touched |
| A subagent "fixes" a decision it was told to preserve | The three deliberate decisions (no `user.*` grant, `registrations` unique, kesiswaan document bypass) stay. A subagent that reports wanting to change one of them is reporting, not asking. |

## 11. Definition of done

- A teacher can enter, edit and publish a grade for their own class
- A parent sees a grade only after it is published
- A teacher can correct a published announcement without re-stamping its date
- An admin can link a parent account to a student
- A file upload cannot escape the media directory or smuggle a script
- PPDB verification records its decisions through the workflow engine
- An operator can toggle a module without a shell
- A staff member can read their own employment record
- **Every permission in the catalogue is either enforced by code or deleted**
- Full suite green, deployed, and `curl`-verified
